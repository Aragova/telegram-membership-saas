# ViMi Pay — удаление бота и полное повторное подключение через Telegram

## Пользовательский сценарий с нуля

1. В центральном `@vimipay_bot` владелец открывает `Мои боты`.
2. Выбирает `🗑 Удалить @имя` и видит отдельный экран последствий.
3. Подтверждает `🗑 Да, удалить бота`. Система перепроверяет его
   полномочия, точный проект и BotInstance, затем помечает подключение
   как `deleting`; новые оплаты блокируются.
4. Supervisor прекращает опрос Telegram этим ботом, дожидается завершения
   обработчика и освобождения проектной advisory lock.
5. Только процесс, заново получивший блокировку, удаляет BotInstance с
   **зашифрованным токеном**. Связанная запись состояния запуска удаляется
   через внешний ключ PostgreSQL `ON DELETE CASCADE`. Глобальная
   уникальность Telegram ID освобождается.
6. Владелец обновляет `Мои боты` и снова подключает тот же Telegram ID
   через BotFather. Можно использовать старый проект (с сохранёнными
   тарифами и финансовой историей) либо `➕ Новый проект с нуля`,
   затем повторить все настройки без SSH/SQL. Число циклов не ограничено.

## Когда удаление заблокировано

Нельзя потерять покупателя с действующим оплаченным доступом:
незакрытые заявки, активные подписки, активные grants, фактически
предоставленные доступы, незавершённые access actions и живые
invite tickets блокируют удаление, с указанием количества причин.
Необходимо корректно завершить обязательства и отзывать доступ,
сохраняя историю платежей. Обычное удаление бота **не** является
сбросом/удалением всех финансовых данных проекта. Удаление действующей
подписки без отзыва доступа запрещено. При новой обязанности, возникшей
в момент переключения, supervisor возвращает бота в `registered`
вместо уничтожения учётных данных.

## Безопасность и ограничения

- Удаление может инициировать только **владелец проекта**, не коллега
  с административной ролью. Callback содержит привязку к UUID проекта и
  BotInstance; старое меню другого проекта не действует.
- Supervisor получает только `(project_id, telegram_bot_id)` по
  `list_customer_bot_removals()` (SECURITY DEFINER; EXECUTE только
  `membership_runtime`). Ciphertext не раскрывается.
- Процесс с незавершённым Telegram polling держит проектную
  PostgreSQL advisory lock; финализация не может пройти раньше остановки.
- Удаление идемпотентно. Запрещено переподключение второго бота, пока
  прежний `deleting`.
- Записи проекта, каналов, тарифов и финансовой истории сохраняются.
  Самого Telegram-бота в BotFather система не удаляет; его можно снова
  подключить или удалить вручную в BotFather.
- Окончательный проектный purge — отдельная, более опасная функция,
  требующая отдельного дизайна, предварительного отзыва доступа и
  подтверждения владельца.

## Проверка

Интеграционный PostgreSQL тест: регистрация, работающая аренда,
проверка авторизации, запрос удаления, невозможность удаления при
активном polling, автоматическая финализация, FK очистка состояния,
повторная регистрация Telegram ID в другом проекте (дважды),
изоляция другого владельца.

Тесты интерфейса: кнопка, подтверждение, отмена, отсутствие кнопки у
посторонних и в состоянии deleting, защита от старой кнопки другого
проекта, отказ при неисполненных обязательствах.

После CI и чистого Codex exact-head review — отдельное разрешение
владельца на merge, затем миграция `0016` и один полный реальный
onboarding через Telegram.
