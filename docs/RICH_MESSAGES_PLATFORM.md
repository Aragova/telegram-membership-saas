# ViMi Pay — единая система Rich Messages

## Продуктовое решение

Rich Messages — **основной формат интерактивных экранов во всей платформе**.
Одинаковая инфраструктура используется центральным `@vimipay_bot`,
собственными ботами администраторов, пользовательскими меню, магазином
файлов, тарифами подписок и закрытой статистикой владельца платформы.

Не нужна настройка отдельно для каждого бота, нет ограничений по количеству
подключённых ботов, нет отдельных таблиц настроек или миграции.

## Обязательное правило оформления новых экранов (2026-11-10)

**Rich-first по умолчанию для всего ViMi Pay.** Любой новый или существенно
изменённый интерактивный экран (центральный бот, режим владельца платформы,
финансы и счета ViMi Pay, администратор подключённого бота, покупатель,
подписки, файлы, статистика, мониторинг) должен использовать единый
Rich-транспорт **и нативную Rich-структуру там, где она улучшает читаемость**:
заголовки, таблицы метрик, тарифы/цены, карточки и разделение блоков.

- **Просто HTML с жирным заголовком не считается готовым Rich-оформлением**
  для экрана с несколькими показателями. Для краткого текста
  без метрик таблица не обязательна. Не копируйте структуру отдельного экрана
  при каждом PR: переиспользуйте существующие общие Rich-рендереры.
- Каждая новая финансовая сводка, в том числе «👑 Платформа → Финансы →
  Счета», обязана отображать метрики в нативной Rich-таблице, когда
  Telegram поддерживает Rich. Реквизиты, подтверждения денег и
  банковские инструкции остаются экранированными и **не изменяют смысл**.
- Не создавать дублирующие кнопки, отдельные финансовые панели,
  дополнительные обработчики или новый глобальный переключатель Rich;
  сохранить существующие callback_data, доступы, RU/EN и навигацию.
- **Критерий приёмки каждого PR с Telegram UI:** тест RU/EN на реальный
  экран и его Rich-структуру, проверка callback-клавиатуры и безопасного
  HTML fallback, визуальная проверка на staging. Отдельно проверить,
  что глобальный Rich-флаг включён, а при переходе на HTML в логах есть
  диагностическая причина. Нельзя считать задачу выполненной лишь потому,
  что общий Rich-транспорт подключён.
- Разумные исключения остаются прежними: ForceReply/ввод данных,
  передача чеков/медиа, пользовательские публикации и простые
  неинтерактивные уведомления. При неподдерживаемом Telegram-клиенте
  или явном отказе Bot API разрешён обычный HTML, **без повторной отправки
  при неизвестном результате сетевого запроса**.
- Правило распространяется и на последующие релизы: при добавлении
  функциональности проверять соответствующий экран, не откладывая
  оформление на отдельный косметический PR.

## Архитектура

- `rich_messages.RichUiBot` — общий отправитель и редактор;
- `telegram_adapter.create_bot` — центральный бот;
- `customer_runtime.ObservedCustomerBot(RichUiBot)` — все клиентские
  боты под supervisor, с сохранением наблюдения за `getUpdates`;
- `RichUiBot.send_message` — Telegram `sendRichMessage` для интерактивных
  экранов с inline-кнопками, `edit_message_text` —
  `editMessageText(rich_message=...)` **в существующем сообщении**;
- автоматическое оформление заголовка, безопасные таблицы для платформенной
  статистики и «Моих покупок»; остальные данные и текст остаются прежними;
- каталог тарифов и карточка конкретного тарифа — нативные Rich-таблицы,
  при этом список цен и методов формируется старыми сервисами;
- страницы магазина файлов, панели администраторов, владельца платформы,
  меню, покупки, модераторы и другие интерактивные формы используют
  универсальный транспорт. Существующие специальные Rich-карточки файлов
  и подписок остаются.

## Каналы: полноценные Rich-карточки

Новые экраны `📢 Каналы` и карточка конкретного канала используют
`send_owner_rich` из общего модуля админского Rich UI вместо неявного
преобразования обычного HTML:

- Список каналов: Rich-заголовок, компактная таблица количества подключений,
  имена каналов остаются на исходных кнопках без дублирования.
- Карточка канала: таблица участников Telegram, активных платных подписчиков,
  покупателей, тарифов, подтверждённых оплат и неоплаченных заявок.
- Финансы: отдельная нативная таблица **валюта / точная сумма / количество
  подтверждённых оплат**, без округления BTC, без пересчёта валют.
- Существующие `callback_data`, кнопки добавления, удаления, обновления
  и возврата не меняются. Серверное правило блокировки удаления при реальных
  покупках остаётся прежним. RU/EN и пользовательские имена экранируются.
- Fallback использует исходный классический HTML при отказе Telegram от
  Rich Messages и глобальное переключение
  `TMS_RICH_MESSAGES_ENABLED=false` без изменения базы.

Эти экраны не добавляют новые SQL-запросы, права доступа или миграции;
только оформление уже существующих данных.

## Инварианты

1. **Не менять callback_data, клавиатуры, цвета кнопок и права доступа.**
2. **Не изменять административные инструкции оплаты или реквизиты**:
   переносим их существующий HTML без переписывания содержимого.
3. Чек по `ForceReply`, служебные запросы ввода текста и передача медиа
   остаются обычными сообщениями.
4. Рекламные/пользовательские публикации, уведомления без интерактивной
   клавиатуры и отложенная доставка файлов не переформатируются.
5. Платёжные сервисы, статусы, доступ в канал, подписки, RLS,
   миграции PostgreSQL и бухгалтерский учёт не изменяются.
6. При явном отказе Bot API от Rich-формата используется прежний HTML.
   **При сетевых сбоях повторной отправки нет**: запрос мог уже дойти.
7. RU/EN выбираются текущей системой локализации.
8. Редактирование Rich-карточек использует существующий `message_id`,
   устраняя накопление старых тарифных клавиатур при навигации.

## Глобальное включение и аварийный возврат

```env
TMS_RICH_MESSAGES_ENABLED=true
```

По умолчанию **true для всех ботов**, включая центральный.
Переменная передаётся в `bot`, `customer-supervisor` и `customer-bot`.
Старые `TMS_RICH_FILE_CHECKOUT_BOT_IDS` и
`TMS_RICH_SUBSCRIPTION_CHECKOUT_BOT_IDS` оставлены для совместимости,
но при наличии глобального переключателя больше не используются.

Чтобы мгновенно вернуть **весь** старый интерфейс на staging,
задайте `TMS_RICH_MESSAGES_ENABLED=false` при пересоздании
соответствующих контейнеров. Нет миграции и потери покупок.
Существующие Rich-сообщения останутся в истории чата, новые экраны
будут открываться в обычном HTML.

## Проверка после merge

1. Ревью exact HEAD, полный CI, unresolved threads=0.
2. Staging: пересобрать центральный `bot` и `customer-supervisor`,
   сохранив `compose.light100.yaml`, без миграций и бэкапов.
3. `@onlyyoufullbot`: RU/EN, `/menu`, каталог валют, выбор тарифа;
   удостовериться, что прошлые кнопки исчезают при переходе.
4. Оплата: реальные банковские инструкции без модификации;
   `Я оплатил` → чек → админское подтверждение/отказ.
5. Файлы: папки, товары, Rich-карточка, выбор способа оплаты, выдача,
   `/myfiles`.
6. Администратор: панель, тарифы, подписчики, статистика, рассылка,
   продажа файлов, модераторы; проверить отсутствие доступа у покупателя.
7. Центр: подключение, управление ботами, платформа, статистика.
8. Проверить работоспособность существующих callback-кнопок и точность
   переводов, а также fallback при неподдерживаемом методе.

Цель — полное, единообразное оформление, **не перепроектирование оплат**.
