# ViMi Pay v2 — история использования и основа SaaS-биллинга (этап E)

## Цель

Владелец ViMi Pay должен видеть историческую активность платформы, в
том числе после удаления подключённого бота, чтобы впоследствии можно
было установить объективные правила тарификации клиентов SaaS.
**Этап E ничего не списывает, не выставляет счёта и не ограничивает доступ.**

### Какие события сохраняются

| Тип | Источник |
|---|---|
| `bot_connected` | успешная вставка BotInstance после проверки токена |
| `bot_deleting` | заявка на корректное удаление |
| `bot_removed` | **фактическое** удаление BotInstance после безопасной остановки |
| `bot_disabled` / `bot_reenabled` | смена статуса подключения |
| `plan_published` | публикация нового или повторно активированного тарифа |
| `customer_joined` | первая регистрация покупателя в проекте |
| `subscription_started` | создание активной подписки |
| `subscription_renewed` | реальное изменение оплачиваемого периода/активация |
| `payment_approved` | создание подтверждённого Payment с валютой/суммой |

**Не трактовать** `bot_deleting` как факт удаления, а
`subscription_started` как число различных покупателей. Эти события
имеют разные значения. Все валюты учитываются раздельно.

### Архитектура

Alembic `0020_platform_usage_metering` добавляет:
- `platform_usage_events` — append-only журнал с project_id и
  историческим BotInstance UUID без внешних ключей на удаляемые
  проект/бота. В записи бота хранится его публичный @username;
  банковских реквизитов, токенов, чеков, персональных данных покупателей
  и текстов инструкций здесь **нет**.
- PostgreSQL AFTER triggers на `bot_instances`, `plans`,
  `payments`, `subscriptions`, `project_customers`.
  Триггеры и журнал находятся **в одной транзакции**: rollback операции
  откатывает событие, повторное создание Payment невозможно из-за
  существующих финансовых ограничений, бессодержательный UPDATE не
  добавляет событий.
- RLS включён с FORCE без разрешающих политик обычному runtime.
  Прямое чтение/запись журнала клиентами и владельцами каналов запрещены;
  только защищённая `SECURITY DEFINER` агрегирующая функция
  `public.platform_usage_snapshot`, проверяющая платфоменного владельца
  по DB ACL, возвращает счётчики/историю и аудирует вызовы.
- Новый пункт `👑 Платформа → 📊 Использование и история`:
  периоды, количество событий каждого типа, подтверждённые платежи
  по валютам, постраничная история ботов, включая удалённые подключения.

Нет нового фонового воркера, периодического опроса Telegram, внешнего
биллинга или дополнительных поставщиков оплаты.

### Совместимость и миграция старых данных

Миграция переносит сохранённые достоверные события из существующих
`bot_instances.created_at`, `payments.approved_at`,
`project_customers.created_at` и дат начала *существующих активных*
подписок. Уникальные event_key предотвращают повторную загрузку
идентичных одноразовых событий.

Историю **удалённых до установки** версии 0020 ботов восстановить
из удалённых записей невозможно — никогда не рисовать фиктивные даты
или общее количество удалений до миграции.
Дата прошлой публикации тарифов и прошлых продлений тоже может не
сохраняться; такие события отслеживаются только после миграции.
Отчёт явно предназначен для точных будущих измерений.

### Подготовка к staging

После одобренного merge выполнить `alembic upgrade head` от
**миграционного** DB пользователя, затем существующий
`python -m telegram_membership_saas.platform_bootstrap` однократно
обновит GRANT EXECUTE для новой функции
`platform_usage_snapshot`. Нужен ранее установленный
`TMS_PLATFORM_OWNER_TELEGRAM_ID`; он не записан в репозиторий.

Проверить два разных Telegram-аккаунта: владелец ViMi Pay видит
метрики и удалённого бота, владелец отдельного канала и покупатель
не могут открыть `plat:usage:...` и не получают данные чужих
проектов. Затем провести полный E2E из чистого подключения,
создание/удаление бота, продажу и проверку доступа.

### Граница с коммерческой монетизацией

Ни одно событие **не является выставленным счётом**.
Для реального SaaS-биллинга отдельно понадобится согласовать
тарификацию, период, льготы, оплату и возвраты самой платформы,
правила для удалений/реактиваций, сверку использования, счета и
юридические обязанности. Клиентский GMV по ручным переводам
**не равен выручке ViMi Pay**.
