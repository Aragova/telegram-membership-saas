## 4. ViMi, ViMi Pay и домен usevimi.ru

- **ViMi Autoposting**: действующий сайт [usevimi.ru](https://usevimi.ru) описывает автоматизацию публикаций, видео и тарифы *другого продукта*. Репозиторий сайта: [Aragova/telegram-forwarder-bot](https://github.com/Aragova/telegram-forwarder-bot), каталог `landing/`, файл `landing/CNAME` содержит `usevimi.ru`.
- **ViMi Pay**: самостоятельная платформа для подключения платных каналов/ботов с подписками и файлами. Центр: [@vimipay_bot](https://t.me/vimipay_bot). Пока сайт должен показывать отдельную вкладку/раздел **«ViMi Pay · Готовится к запуску»**, а не притворяться завершённой публичной продажей или указывать неподтверждённые лимиты.
- Для новой инфраструктуры **не менять DNS корня `usevimi.ru`**: это может выключить существующий сайт. Предварительный выбор: поддомен `api.usevimi.ru` для будущего HTTPS API/webhook ingress; финальное имя и сетевую схему утвердить до настройки.
- **Постоянный публичный IPv4:** сначала проверить адрес и провайдера VM, затем закрепить/резервировать IPv4 в панели хостинга. Указывать в DNS `A api.usevimi.ru → <проверенный резервный публичный IPv4>` только после получения адреса; TTL во время миграции 300 секунд. Если адрес уже выделен статически, не покупать второй без необходимости. Не публиковать частный IP. AAAA добавлять только при исправной IPv6-маршрутизации.
- **HTTPS:** TLS-сертификат, reverse proxy, ограничение портов, rate limiting, валидация webhook секретов, health/readiness и логирование без секретов. Избегать размещения самого webhook на существующей странице с клиентским JavaScript. Старый сайт оставить на прежнем хостинге.
- Доступ к DNS-регистратору и панели VM **не подтверждён**. Никаких изменений IP, DNS, SSH или SSL этим документационным PR не выполняется.

## 5. lava.top: текущий статус и гипотеза интеграции

Пользователь сообщил существующую страницу [app.lava.top/146978276](https://app.lava.top/146978276). **Не подтверждено**, что публичная страница означает активную учётную запись с разрешённой API-интеграцией, выставлением счетов или API-ключом. Личный кабинет не доступен для аудита.

- По [официальному описанию API lava.top](https://developers.lava.top/en) доступны продукты, счета, подписки, отчёты и webhooks; провайдер следует проверить на пригодность **именно для SaaS-счетов самой ViMi Pay** (не смешивать с пользовательскими платёжными способами чужих подключённых ботов).
- Проверить разрешённые категории услуг, комиссии и валюты в кабинете, KYC/ограничения, статус аккаунта, webhooks, возвраты, рекуррентность и API. `lava.top` и `lava.ru` — **разные продукты**, не подменять один другим.
- Не вводить API-ключи в GitHub/чат. Не принимать success redirect как доказательство оплаты: только проверенный webhook и/или authenticated provider API + локальная уникальная ссылка на платёжный источник + идемпотентная фиксация.
- Любая будущая интеграция: отдельный дизайн и тесты, ручная проверка чеков продолжает работать до безопасного switch-over. Никаких автоматических начислений только из наличия ссылки Lava.

## 6. Архитектура следующего этапа (пока не внедрять)

- До 100 малонагруженных ботов: замеры live `light100`, PostgreSQL, polling API latency и очередей; без выдуманной гарантии ёмкости.
- 100–300: независимые Supervisor группы, bounded async execution, справедливое распределение нагрузки и транзакционные очереди.
- Далее: отдельная ingress-модель `polling/webhook`, dedup `(bot_id, update_id)`, durable event inbox, быстрый приоритет платежного `pre_checkout_query`, safe polling↔webhook cutover/rollback.
- Между очередью и финансовыми обработчиками сохранять PostgreSQL RLS, idempotency, исторические sale/payment источники и правила очередности. Никаких широких `asyncio.create_task` без ограничений или «многопоточности» за счёт целостности платежей.
